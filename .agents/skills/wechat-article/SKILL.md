# 微信公众号文章写作

先确定场景和交付意图，复用已有需求与来源，只询问影响推进的缺失信息。用户本次要求优先；写作不包含登录公众号、上传素材或对外发布。

## 场景与意图

| 场景 ID | 识别依据 | 按需读取 |
| --- | --- | --- |
| `openjiuwen` | 明确为 openJiuwen 公众号写作，或以 openJiuwen／WorkSwarm 相关能力为主体传播 | [场景约定](references/scenarios/openjiuwen.md) |

以指定公众号、用途及受众为准，不因材料提到品牌就选中场景。本项目没有其他场景线索时可说明采用 `openjiuwen`；明确为其他用途时按通用流程执行，不套品牌口吻、不自动新增场景。需要借鉴时按场景索引读取相关段落，不默认加载全部样文或遍历仓库。

| 意图 | 交付边界 |
| --- | --- |
| 技术素材准备 | 整理技术事实、可写主张、案例和引用。用户要求落盘时归档到主题的 `refs/`，可单独交付 |
| 选题策划 | 给读者问题、主张、证据和角度，不默认展开全文 |
| 标题、摘要或单独导语 | 围绕同一事实主线提供候选，按要求控制长度；不自动启动整篇审批 |
| 大纲 | 完整工作稿供选择与调整，最终确认后归档，不提前写正文 |
| 新稿、完整改编或重写 | 先确认大纲，按导语及主章节逐一写作、处理配图并取得确认，再汇总 |
| 修改润色 | 只改指定范围；应用到文件时按版本规则处理，受影响章节确认，不扩成全文重写 |
| 审稿与核查 | 指出事实、论证或表达问题，不自动改正文、补大纲或清理资产 |

多个意图可组合；“直接成稿”不替代大纲或章节批准。纯建议、纯审稿与仅聊天交付不自动创建版本目录。

## 先收集必要信息

信息不足时可一次引导，允许自由描述，不要求逐项填表：

> 请介绍主题、希望覆盖的内容和写作目的，并提供已有的参考资料。如果希望核对具体实现，可以提供代码仓链接或本地路径，也可以跳过源码核对。
>
> 参考资料和相关代码至少有一项可读取、与主题相关；只有主题名称或模仿文风的样文不足以支撑事实写作。

- 相关产品说明、原稿、实验记录或代码任一项可以满足门槛，不强求资料与代码同时具备。两者均无有效内容时先补来源，可继续讨论选题，不编写未经支持的事实稿。
- 复用对话中已明确指定的代码仓。未指定且源码会影响结论时，可引导用户提供一次，并允许跳过。未获指定时不自行搜索、选用或下载代码仓。用户跳过后按已有材料推进，标明缺少源码依据的结论。
- 局部改稿可用原稿作为输入，但其中事实不自动视为已核实；不新增事实时不重复收集新稿需求。
- 已有读者、目的和范围直接沿用。可在大纲中按需安排章节详略、主要信息增量和转场，减少逐章确认后的返工，不新增篇幅审批或固定字数要求。
- 资料可包括设计方案、竞品特性宣发软文、测试记录；需要差异化建议时，以本方代码及相关资料对照竞品材料，不要求本方宣发软文，也不强制收集一套竞品资料。软文主题、资料分类与原文归档各按[分层目录规范](references/versioning.md#目录)命名。

## 按当前阶段执行

| 当前任务 | 读取与执行 |
| --- | --- |
| 技术素材准备 | 按[事实与表达](references/facts-and-style.md#技术素材准备)划定证据范围。用户指定源码时交给 code-understanding 取证，再按[参考材料归档](references/versioning.md#参考材料与历史追溯)交付 |
| 任何文章文字生成、改写或事实核查 | [事实与表达](references/facts-and-style.md)：按目标版本取证；提供相关代码仓且涉及实现时回查源码，可使用代码理解技能；humanizer 润色后保留技术事实及条件 |
| 新建或改变大纲 | [大纲流程](references/outline-workflow.md)及场景模板：标题可选，正文导语和各节概述具体；完整大纲最终确认后才归档、写正文 |
| 写正文或改稿 | [逐章流程](references/chapter-workflow.md)：写前回查本章可用来源，写后润色、核查、处理配图并确认，之后才继续下一章；视频最后统一引导添加 |
| 创建或接续文件版本 | [版本管理](references/versioning.md)：先选正确基线，不重写历史；工作稿与正式版本分开，正文绑定真实大纲 |
| 制作、采用或清理媒体 | [媒体规范](references/media-workflow.md)：编号、标题与文件名一致，正文为 PNG，可保留对应 SVG；保护正文、大纲及已选封面，未引用候选先暂存，正式完稿后清理 |
| 保存工作进度、核对归档或恢复中断 | [状态契约与工具](references/state-contract.md)：使用完整契约和章节定位标记；默认只读检查，只有明确操作命令才写入、移动或删除 |

按当前任务读取所需文档，不默认加载全部流程或运行全部命令。事实依据在“事实与表达”维护，确认边界在大纲／章节流程及媒体规范维护，文件映射在版本管理维护，字段与脚本操作在状态契约维护。模板、大纲、章节确认各有范围，不增加例行全文或清理审批。

## 交付检查

素材准备按参考材料的交付要求检查证据和链接。大纲确认、章节确认与版本检查适用于对应的写作阶段。

- 主张、数据、标题及图注有对应证据；代码版本、条件、依赖和限制准确，用户明确允许的实现差异有范围记录。
- 大纲及本次受影响章节有真实确认，汇总未暗改已确认文字，humanizer 没有扩大能力或丢失条件。
- 正文使用唯一文章 H1、主章节 H2、子章节 H3；只保留读者需要的内容，内部核对说明和状态留在正文之外。
- 落盘任务用工具检查文件、版本映射、确认摘要、媒体命名／正文 PNG、来源及保留集合；纯聊天或建议不启动状态工具。工具检查不替代取证或用户确认。
- 落盘交付提供版本、映射、实际路径及待补项；清理只报告实际结果，不将阶段稿说成正式完稿。仅聊天或建议任务不虚报保存记录。

仅需获取网页时使用 `web-article-fetcher`，普通核查不自动下载全部文章。新增场景时按实际需求增加 `references/scenarios/` 文档及路由，通用规则保留一处，不预置无用场景。
