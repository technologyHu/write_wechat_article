# HTML 大纲确认向导

按[大纲流程](outline-workflow.md#与用户协作)选定当前阶段。标题阶段每轮只展示并提交一个标题项。内容阶段在左侧大纲目录点击导语、章或子章，逐项查看概述、提交修改意见或确认。目录和概述都显示内容确认状态。主章有子章节时，先在该章概述页选择是否添加章导语。对话收到回复后在同一个页面更新内容。

## 准备内容

| 阶段 `stage` | 页面内容 | 对话收到回复后 |
| --- | --- | --- |
| `titles` | 当前的一个标题项。按文章标题、章标题、子章节标题的顺序展示。每项有 2–3 个候选，推荐放首位。可选择、自拟或提交重拟方向 | 选择或自拟即确认该项，再推进到下一个未确认项。要求重拟时停在当前项，换一轮候选 |
| `sections` | 逐项展示导语、章及子章节的概述和媒体安排，已确认内容可从同一目录回看 | 记录确认并默认打开首个待核对项。收到意见后修订当前项并重新展示。全部实际内容获确认后准备完整稿 |
| `final` | 一次展示完整待确认 Markdown，包括内部依据。修改意见始终展开，宽屏放在随阅读滚动保持可见的右栏，窄屏放在正文前。修改提交和整稿确认分别操作 | 用户发出的确认须对应当时展示的确切版本。确认后按版本流程归档或锁定聊天基线 |

用在本篇内唯一的 `review_id` 标识每次展示，如 `swarm-ext-titles-r1`。标题项和内容项使用稳定、易回指的 ID，如 `T`、`C2`、`C4.1`。保留渲染时的原始 JSON，用于校验回传和定位展示内容。相同轮次再次展示时复用原页面。展示内容有变化时另起轮次。

标题阶段的 `select` 表示选择已展示候选，`custom` 表示给出自拟标题。内容阶段的 `accept` 表示采用该轮该项的具体安排。各阶段的 `revise` 都表示要求修改，完成修改后重新展示并取得确认。未提交的项仍待确认。同一项填了修改意见时按意见处理。沿用已确认且未受影响的项。用户要求修改标题或内容时，回到对应阶段并重开受影响的项。只有最终阶段的 `confirm` 可以确认完整版本。

## 渲染和回传

1. 为本篇选定一个固定的页面路径，例如 `.tmp/outline-review/outline-review-current.html`。每轮先保存单独的轮次 JSON，再运行 `python -B <skill-dir>/scripts/render_outline_review.py <轮次 JSON 路径或 -> <固定 HTML 路径> --publish-current`，同时更新自包含 HTML 和同名的当前 JSON。两份输出放在本篇 `.tmp` 时会自动登记，可用 `--version` 指定稿次对应的版本。单独生成的轮次 JSON 需要随完稿清理时，用 `register-temp` 登记。输入为 `-` 时从标准输入读取 UTF-8。
2. 给用户固定的手动链接。后续轮次更新原页面，保持同一标签页。独立 HTML 需要在原标签页刷新，远端下载版需要用最新版文件替换原文件。首次确有需要且用户要求时才打开浏览器。没有文件交付能力时，在聊天里按相同顺序逐项确认。
3. 独立浏览器版点「生成反馈」，再复制完整 JSON 粘贴到原对话，或下载 JSON 后上传。有宿主回传能力时，页面显示「提交反馈」并保留复制入口。可按[本机浏览器一键回传](#本机浏览器一键回传)复用服务，也可按 visualize 技能生成[对话内片段](../assets/outlines/outline-review.html)。两种方式传送同一份 JSON，页面用语与具体应用解耦。只有实际收到用户反馈后才推进。
4. 收到粘贴、下载或宿主回传的 JSON，使用原轮次输入校验。运行 `python <skill-dir>/scripts/validate_outline_feedback.py <当前轮次 JSON> <反馈 JSON 文件或 ->`，其中 `-` 接收完整粘贴文本，也接受用 Markdown JSON 代码块包裹的文本。通过后应用返回的决定。轮次、阶段、条目或动作不匹配时，提供当前轮次的页面并请用户重发。用户直接用自然语言回复时，按当前展示范围理解明确的选择和修改意见。
5. 最终确认前复核当前 `review_id` 指向的全文，确保它对应实际展示的完整稿。工作稿已有变动时，重新展示修订稿。反馈校验只检查格式及适用范围，用户实际发回的回复才是确认记录。HTML 与 JSON 属于协作材料，文章版本和媒体记录按原流程管理。

对局部修改使用校验命令的 `--targets`，以返回的 `stage`、`id` 和 `label` 锁定条目。反馈文字与条目所指不同且不明确时，先核对范围。用户说「基于 B，前半句保留」时，在新轮次添加 `title_revision`，记录上一轮 `review_id`、`candidate`（A/B/C）、`base_title`、可选的 `locked_prefix`／`locked_suffix`，并用渲染命令的 `--previous <上一轮 JSON>` 核对。用户切换到对话时，后续轮次可在原评审数据上标记 `channel: "chat"`，复用同一确认规则且禁止渲染页面；只有用户明确切回才恢复网页。

### 本机浏览器一键回传

- 在本机工作区运行 `python -B <skill-dir>/scripts/serve_outline_review.py <固定 HTML 对应的当前 JSON>`，整篇复用该服务。当前 Codex 适配器使用工具环境的 `CODEX_THREAD_ID` 和支持 `queue` 的本机 CLI。浏览器与服务须在同一台机器。读取启动输出的 `url`，检查可达后，把完整 URL 和独立 HTML 链接交给用户。URL 自带随机路径，只在该对话中分享。
- 收到反馈后发布下一轮到同一当前路径。页面检测到新轮次会原位更新，原 URL、标签页和服务可继续使用。服务只接受本机同源请求，连续两小时没有轮次更新或提交后自动停止。服务退出后需要重启时，用 `--reuse-url <先前服务 URL>` 恢复原地址。
- 用户点击「提交反馈」后，服务校验当前轮次和反馈，用 `codex queue --thread <当前会话 UUID> --message <反馈 JSON>` 排入当前对话。客户端空闲后处理队列。每轮只接受首次有效提交；服务同址重启时读回本机提交摘要，已排队的相同反馈只返回原状态，状态不明时先查看原对话。
- 启动、连接或提交失败时使用「复制反馈」。送达状态不明确时先查看原对话，避免重复发送。缺少本机 Codex CLI、可信的当前会话 ID 或本机浏览器连接时，使用自包含 HTML。此路径借鉴 [Superpowers Visual Companion](https://github.com/obra/superpowers/blob/main/skills/brainstorming/visual-companion.md) 的本机服务和按轮次接收反馈方式。Codex 队列用法见[官方开发者命令](https://learn.chatgpt.com/docs/developer-commands#codex-queue)。

前端把确认结果已提交、服务断开和实际已确认分别显示。断开后继续保留当前表单及复制入口。同一标签页刷新同轮时可恢复浏览器会话里的草稿；出现新轮次且本轮仍有未提交输入时，先提示复制，再由用户刷新。旧轮反馈仍受服务端轮次校验。

标题阶段示例。每轮的 `groups` 只有一个分组和一个可提交的标题项。用 `title_step` 标记当前项在标题序列中的位置。同一标题重拟时保留 `id` 和 `title_step`，换新的 `review_id`。

`title_outline` 是左侧目录的数据，从文章标题根节点开始，章和子章通过 `children` 表达。它覆盖本篇全部标题。已确认的节点写入用户选定的标题并将 `confirmed` 设为 `true`。待确认节点显示暂拟标题，若已有候选则显示推荐候选。当前项由本轮 `groups` 中的 ID 标记。目录只展示状态和层级。后续大纲内容和最终稿阶段也可保留该目录。

```json
{
  "stage": "titles",
  "review_id": "swarm-ext-titles-r1",
  "title_step": {"index": 1, "total": 1},
  "title_outline": {
    "id": "T",
    "label": "文章标题",
    "title": "Agent 可以把自己改成什么样？",
    "confirmed": false,
    "children": []
  },
  "groups": [
    {
      "label": "文章标题",
      "items": [
        {
          "id": "T",
          "label": "文章标题",
          "options": [
            {"title": "Agent 可以把自己改成什么样？", "note": "用问题带入自我改造"},
            {"title": "从桌宠到 Token Weather", "note": "以两个演示串起文章"}
          ]
        }
      ]
    }
  ]
}
```

`sections` 设 `section_mode: "individual"`，沿用 `groups` 组织章节层级。每组首项为主章，可紧接章导语，然后是实际子章。各项用 `body` 字符串保存概述和媒体。主章和子章沿用 `title_outline` 的 ID，文章标题节点的 ID 对应全文导语。每轮保留所有项，收到实际 `accept` 后将对应概述设为 `confirmed: true`。内容发生变化时将受影响的概述设回待确认。

有子章节的主章项设 `chapter_intro: null`，首次确认该主章时，`accept` 须附 `chapter_intro: true`（添加）或 `false`（直接进入子章）。收到添加选择后，在该组第二项加入章导语概述，设置独立 ID（如 `C3-intro`）和 `chapter_intro_for: "C3"`。目录把它放在主章下、首个子章前，原页先核对此项。章导语概述通过普通 `accept` 独立确认，随后逐项确认子章。选择直接进入子章时记录安排。两种安排都带入完整大纲。旧轮次沿用其原有反馈契约。

`final` 提供 `stage`、`review_id`、`markdown` 和可选的 `title_outline`。其中 `markdown` 必须是待确认的完整文本，并与后续锁定的内容一致。

最终预览从 Markdown 的各级标题、全文导语和「章导语概述」生成可点击目录。目录只显示标题，点击直接定位到完整大纲中的对应位置。全文导语放在文章标题之后，章导语概述放在所属章的首个子章节之前。

最终预览的修改意见入口同时接收标题和内容反馈。提示用户注明文章标题或具体章、节，并填写新标题或修改方向。收到标题修改后按大纲流程重新确认受影响的标题。

页面生成的反馈示例。标题阶段只提交当前项的决定，可附 `structure_note` 和 `chapter_feedback`。前者用于调整章节顺序和层级，后者可对多个章或子章节标题提出修改意见。只提交意见时继续停留在当前项。批量意见用于更新候选，逐项确认仍以 `decisions` 为准。最终阶段只接受一条 `id` 为 `outline` 的决定。选择候选、自拟标题和修改意见带 `value`，采用内容和确认全文只带 `id` 与 `decision`。

处理 `chapter_feedback` 时，按用户明确指出的章节编号或范围调整候选。已确认项只有在用户明确要求重开时才重新进入确认流程。新候选的推荐项同步到目录，后续逐项展示和确认。

```json
{
  "format": "wechat-article-outline-feedback/v1",
  "review_id": "swarm-ext-titles-r1",
  "stage": "titles",
  "decisions": [
    {"id": "T", "decision": "revise", "value": "保留桌宠例子，把标题再缩短一些。"}
  ]
}
```
