# 目录与版本管理

用于落盘任务的目录、基线、版本和映射。任务范围按[入口](../SKILL.md)确定；大纲确认、逐章确认和媒体处理分别见[大纲流程](outline-workflow.md)、[章节流程](chapter-workflow.md)和[媒体规范](media-workflow.md)。本文件不另设写作或审批流程。

## 适用范围

只讨论选题、候选标题、摘要、局部替换建议、纯审稿或明确仅聊天交付时，不自动建目录、分配版本或清理素材。用户要求保存参考资料时执行参考材料归档，要求保存或应用到稿件时执行相应版本流程。未指定稿件的粘贴原稿润色保持原范围。仅聊天的新稿仍按大纲及章节流程确认。

## 目录

```text
<写作项目根>/
└── <场景 ID>/                       # 如 general 或 openjiuwen
    └── <主题>/                      # 稳定主题名，可用中文或英文
        ├── refs/                    # 本篇资料及来源记录，分类目录按需
        │   ├── design/              # 设计方案
        │   ├── code-analysis/       # 源码分析和引用索引，按需
        │   ├── competitor-articles/ # 竞品特性宣发软文
        │   │   └── <原文标题>/      # 每篇抓取文章的独立归档
        │   │       ├── article.md
        │   │       ├── metadata.json
        │   │       └── assets/images/
        │   └── evaluations/         # 测试与评测，按需
        ├── article/
        │   ├── progress.json
        │   ├── metadata.json
        │   └── v001/
        │       ├── outline-working.md   # 本版待确认大纲，按需
        │       ├── outline-v001.md
        │       ├── article-working.md   # 本版逐章工作稿
        │       ├── article-v001.md
        │       └── assets/
        │           ├── images/        # 图片及必要源文件
        │           └── videos/        # 本地视频
        ├── exports/                 # 正文 ZIP，实际导出时创建
        └── .tmp/                    # 本篇候选及废图暂存，按需
```

| 层级／用途 | 命名规则 | 示例 |
| --- | --- | --- |
| 场景目录 | 英文场景 ID | `general/`、`openjiuwen/` |
| 文章主题目录 | 稳定、合法、可辨认的中文或英文名，优先沿用用户指定名称 | `扩展性特性宣发软文/`、`extensibility/` |
| 自建资料分类目录 | 英文，细分分类也沿用英文；小写字母、数字和连字符 | `refs/design/`、`refs/competitor-articles/` |
| 抓取文章归档目录 | 使用原文标题，保留原语言，不受分类目录英文规则影响 | `refs/competitor-articles/<原文标题>/` |
| 固定工作与资产目录 | 沿用既定名称 | `refs/`、`article/`、`exports/`、`.tmp/`、`assets/images/`、`assets/videos/` |

- 使用英文的场景、主题或分类名时采用小写字母、数字和连字符。通用新稿可归档到 `general/<主题>/`，优先采用用户指定的位置。输出根默认是本技能所在文章项目；进入代码仓分析时，写作输出仍保存在原项目。
- 修改文章标题不自动改变稳定主题目录。续写复用指定稿件目录，独立新文章使用独立目录，不能仅凭同题合并。文章标题和媒体标题可用中文。
- 落盘写作在确定主题和基线后，准备对应的 `article/vNNN/`。大纲和正文放在该目录，图片和视频放在其 `assets/images/` 和 `assets/videos/`。继续同一轮时复用该版本目录。

### 参考材料与历史追溯

- `refs/` 按资料用途设置英文分类目录，如 `design/`、`competitor-articles/`、`code-analysis/` 或 `evaluations/`。按需建立和细分，优先使用用户指定位置或已有目录。原始资料文件名、第三方归档及技能内历史样文结构保留。
- 源码素材可放在 `refs/code-analysis/`。单一问题可写在一份文档里，多仓或多案例可按用途拆分并设置索引。仅归档参考材料时，在主题目录的 `refs/` 内交付即可，稿件版本在相应写作阶段登记。
- 抓取文章的标题清理、重名、无标题回退及显式指定子目录名，统一按[网页抓取技能](../../web-article-fetcher/SKILL.md#标题目录)执行；将所选分类目录作为抓取命令的父目录，不把英文分类规则传成文章名覆盖值。抓取归档的 `metadata.json` 仅记录来源和抓取状态，不混入本篇 `article/metadata.json` 的版本历史。
- 外部文件和代码仓保留原位。来源可记在素材文档、索引或既有 `refs/sources.md` 中。源码引用按[代码理解证据规则](../../code-understanding/references/explanation.md#证据)保存本地跳转和可重定位信息，便于临时 checkout 移走后复核。易变且影响结论的材料可按需保留片段或副本。
- 交付前检查 Markdown 内链、源码引用的目标文件和行号，以及版本与仓内定位是否对应。源码目标暂不可访问时，保留可重定位信息并标明验证缺口。
- [共享样文](samples/openjiuwen/index.md)及其来源元数据是输入，不进入本篇版本历史；作为改编原稿时仍需自己的确认大纲。样文事实与媒体的取用按[事实规范](facts-and-style.md)核查。
- 本地链接相对于实际文件所在目录解析。新大纲的工作稿和版本大纲使用同一目录下的链接。迁移旧大纲时核对链接目标与登记散列，再更新元数据路径。复用媒体在本版建立规范副本并记来源，保留历史版本依赖。
- 后续阅读和核查记入工作上下文或来源记录；是否需要新大纲按[确认后的变更](outline-workflow.md#确认后的变更)判断，不回填已归档大纲。

## 统一命名

- 大纲为 `article/vNNN/outline-vNNN.md`，正文为 `article/vNNN/article-vNNN.md`，默认使用同一版本号，从 `v001` 开始。既有不同编号的映射及旧目录按元数据识别。
- 同一轮写作内，已确认的修订合并到当前对应版本。需要新增大纲或正文版本时，先说明拟用编号、变更范围及对应关系，得到用户确认后再创建。用户已明确要求新建时直接执行。
- 同轮的标题标点、指定大纲字段同步、占位落实、媒体显示编号和图注修改沿用当前稿及其版本目录。讨论稿次、媒体修订和文章版本独立。已正式交付的历史快照继续保留；需要从交付稿开新版本时，先按本条确认编号。
- 获准新增时检查现有版本记录、子目录和平铺文件，采用可用的下一编号。预留目录和工作稿不计入正式版本。已交付文件按原记录保留，用户明确要求合并、覆盖或删除时按其指示处理。
- 媒体采用[独立编号与修订号](media-workflow.md)，不能覆盖历史引用的资产。

## 大纲与正文协同

### 选择基线

| 本次意图 | 使用基线 |
| --- | --- |
| 全新文章 | 完成大纲确认及归档后展开 |
| 按大纲展开／重写 | 指定已确认大纲优先，否则取最新已确认大纲；指定的是待确认稿时先完成该稿确认，不换成其他版本 |
| 接续正在写作的工作稿 | 读取该稿 `progress.json`、工作正文及绑定大纲，从首个未完成单元继续 |
| 修改或补充正式正文 | 指定正文优先，否则取最新正文；使用它绑定的大纲，不自动切换到最新大纲 |
| 讨论或修改大纲 | 讨论沿用当前明确工作稿；修改正式稿时指定大纲优先，否则取最新已确认大纲 |

同时读取记录和对应文件，不凭编号相同推断映射。只有多个对象或基线确实无法判定时再询问；不覆盖另一个活动稿件。

### 章节工作稿与确认记录

新一轮正文工作稿保存在 `article/vNNN/article-working.md`，进度保存在 `article/progress.json`。按[状态契约](state-contract.md)记录真实确认、未改文字继承和媒体更新；跨大纲复用时，只有未改且仍适用的章节可仅补适用性核对，改动章节仍按章节流程确认。活动会话归属、摘要及恢复细节统一在契约维护。

`save-work --apply` 自带候选校验和双文件提交。中断时使用 `recover`。`assemble` 用于查看候选正文和章节区间。要归档时，用 `archive <软文目录> --version <vNNN>` 检查正文、确认记录与媒体状态，获授权后加 `--apply`。它将正式正文、版本快照和工作状态作为同一批写入；中断时可用 `recover` 续做。

用户明确批准当前稿件完稿时，用 `finalize` 以实际回复记录当前稿的确认，校验媒体待办，归档指定版本、写入 `finalized` 并导出正式 ZIP。省略 `--apply` 可查看涉及的章节、正文散列和导出路径。手改章节有旧快照时提供差异，缺少旧快照时提供现稿和现稿散列。导出遇到 I/O 错误时，用相同版本重试，沿用已归档的正文。

```powershell
python -B -X utf8 .agents/skills/wechat-article/scripts/article_workflow.py finalize '<软文目录>' --version v001 --basis '<用户完稿回复>' --apply
```

用户明确要求完稿后清理时，在 `finalize` 命令上加 `--cleanup`。预览列出拟删除文件、散列、保留文件和原因。正式 ZIP 导出并校验通过后，重新核对引用及文件散列，清理本版正文及大纲工作稿、`.drafts` 和 `.tmp` 中已登记且不再被引用的中间产物。正式稿、大纲、引用素材及源文件和导出包受保护。清理结果列出已删除、保留和失败项。

`edit-section` 和 `edit-caption` 只修改活动工作稿和进度。正文讨论快照放在当前正文目录的 `.drafts/`，只用于逐单元恢复，独立于正式版本与媒体候选。媒体改名按[媒体规范](media-workflow.md)更新实际引用。

用户要求清理已完稿版本的工作稿和 `.drafts` 时，先校验正式正文、大纲、引用媒体、配套源文件和已有导出包，再按指定范围删除工作稿和讨论快照。保留版本与完稿记录，清理后用 `check` 直接核对归档正文。

### 写作与同步

1. 大纲变更按大纲流程确认并保存到本轮对应的大纲版本。获准新增版本时，保存新文件及确认记录并更新最新大纲指针。
2. 按章节流程推进正文。全部所需确认、媒体处置及全文检查完成后，保存新正文和完整快照，登记其 `outline_version` 并更新最新正文指针。尚未完成则只保留工作进度；只要大纲时停在上一步。
3. 内容变化按大纲变更规则同步，旧正文映射不改。用户要求清理时，按[媒体规范](media-workflow.md)核对保留范围后执行。

## 正文目录内的元数据

统一使用 UTF-8 的 `article/metadata.json`，字段和兼容规则以[状态契约及完整示例](state-contract.md#唯一数据契约)为准。

- `outlines`、`articles` 保留全部正式版本；`based_on` 是真实同类基线，首次为 `null`，其他基线须存在且早于当前版本。每条正文的 `outline_version` 指向实际确认大纲。
- `latest_outline_version`、`latest_article_version` 分别取同类最大已交付编号；仅有大纲时正文列表为空、正文指针为 `null`。它们不表示彼此绑定。
- 记录的 `file` 相对于 `article/`、使用 `/` 且仍在本篇目录内；`scenario` 与实际场景一致。大纲／正文标题与对应文件一致，字节散列保护已归档内容。
- 正文保存章节确认／继承、区间、来源、媒体与待办快照。纯素材维护仅追加 `asset_maintenance`，不推进版本；纠错可用 `repairs` 保留原值和原因，不借此重写历史。
- 归档先保存新文件，再用临时 JSON 原子替换元数据。中断后核对文件、真实确认和映射再恢复登记；未知或未完成文件不当作已交付。工作稿双文件提交按状态工具协议执行。

## 导出指定版本

```powershell
python -B -X utf8 .agents/skills/wechat-article/scripts/article_workflow.py export '<软文目录>' --version v001 --apply
```

- 指定真实正文版本。已登记的归档正文优先；该版尚未归档时，可导出进度指向的同编号活动稿，并在交付时标明是工作稿。结果列出待确认单元、确认后手动改过的章节、可见媒体占位和待补媒体。工作稿 ZIP 去除内部章节标记，保留正文里的现有占位。用户明确要发布版时加 `--release`，核对归档正文、章节确认和已有最终占位许可。
- 默认写到软文目录的 `exports/`，首次实际导出时创建。包名为 `<软文目录名><版本号>.zip`，如 `扩展性特性宣发软文v001.zip`。用 `--output-dir` 指定其他已存在的目录。省略 `--apply` 可查看拟打包的正文、资产和目标路径。
- 包内保留 `article/` 下的相对结构，解压后从返回的 `body` 路径打开 Markdown。仅打包该篇正文和通过 Markdown 链接、HTML 媒体标签及所引用 SVG 递归找到的 `assets/` 文件。线上链接和内嵌数据随正文保留。同目录的大纲和大纲工作稿均不入包。
- 缺少文件、路径无法移植或本地链接指向资产目录以外时，先修复引用再导出。再次导出同一版本时沿用同一 ZIP 路径，校验新包的成员、链接和完整性后覆盖旧包。导出不改变原正文、素材或确认状态。

## 旧稿接续

- 保留原文件；纳入本篇时保存副本并记录原路径，只登记实际可核对的版本，不凭文件名重建历史。
- 缺少大纲时从原稿提取结构，注明“根据原稿补建”，展示并取得最终确认后归档，不声称它指导过历史写作。已有大纲但缺确认依据时，同样展示现稿取得当前确认，保存基线新版本，不倒填历史批准。
- 首次纳入确认流程可在文字未变时新增确认版；后续正文指向新基线，旧映射保持原状。本次局部改稿不扩写范围外正文。
- 元数据无法解析或登记文件缺失时，核对并修复后再分配版本；纯审稿只报告。旧契约升级按状态契约处理，未要求接续的目录不自动迁移。

## 交付检查

稿件归档使用 `check` 核对落盘一致性。事实判断、大纲内容清单、章节及媒体确认分别按对应流程复核。重点确认正文使用的是实际绑定大纲、历史依赖仍有效，以及素材整理发生在正确阶段。稿件交付说明版本、映射、路径与待补项。仅归档参考材料时检查来源和链接，交付素材路径及证据缺口。
