# openJiuwen 公众号场景

用于 openJiuwen 及其相关技术、产品和社区能力的公众号文章。以下默认值来自本仓库已有样文的归纳，不代表用户已确认的品牌规范；本次写作要求与新材料优先。

## 受众与目标

默认面向关注 Agent 的开发者、技术决策者和实际使用者。让读者理解一个具体问题、openJiuwen 相关能力如何解决它、已有证据及体验或参与方式。偏技术的主题解释机制与接入价值，偏产品的主题强调任务过程和交付结果。

技术宣传可以鲜明、有吸引力，但卖点要落到可核对的机制、操作或结果上。通用的资料门槛、事实核查、代码对齐及 humanizer 流程统一遵循[技能入口](../../SKILL.md)，本文件仅补充该场景的写作选择。

- 确认依据：用户原话“确认无误，模板和样文引用就按现在的版本，删除项目根目录下的 refs 目录。”本次批准对应模板及样文引用，不代替后续具体文章的大纲确认。

### 子章节写作方式

| 写法 | 适用情况 | 展开逻辑 |
| --- | --- | --- |
| 任务案例 | 让读者理解能力在工作中怎样发挥作用 | 任务目标与约束 → 关键推进过程 → 交付结果 → 对读者的价值 |
| 机制解释 | 解释技术设计怎样支撑某项能力 | 能力要求或任务约束 → 设计选择 → 实际职责、数据流或状态处理 → 可观察行为与成立条件 |
| 差异点论证 | 突出某项竞争力或区别 | 读者的选择标准 → 具体差异及依据 → 任务中的价值 → 比较范围与边界 |
| 演示带入 | 视频或界面中的现象最有说服力 | 提出观察问题 → 安排演示与观察点 → 解释所见现象 → 回扣本节判断 |
| 对照验证 | 有可比条件和实际记录 | 交代比较对象与条件 → 呈现不同结果 → 解释差别 → 限定结论 |
| 多场景并列 | 同一能力服务多类需求 | 确定共同问题 → 选择互补场景 → 比较各自体现的价值 → 归纳共性及差别 |
| 角色或资源分工 | 介绍协作、架构或生态资产 | 各自解决什么问题 → 如何配合或流转 → 用一项任务串联 → 说明依赖与边界 |
| 使用与接入 | 引导体验、开发或参与 | 判断适用对象 → 准备与入口 → 最少关键操作 → 核对结果或进一步行动 |

这些写法用于确认前的规划，不直接充当文章标题，也不是必须使用的检查清单。可单独采用、在同章搭配，或在同一节融合；具体概述说明已经选定的思路，不照抄箭头和固定句式。大纲确认后，正文按确定的论证逻辑展开；改变写法若影响论证路线，按通用变更流程重新确认。

需要判断单任务贯穿、互补 case 并列、同任务逐步扩展或资源流转是否适合本篇时，使用[组织方式的取舍](../samples/openjiuwen/writing-guide.md#组织方式的取舍)。按其适用条件选用，并检查各章是否回答不同问题；组合写法不改变本场景的逐项演示要求。

## 样文选择

需要借鉴时，从技能内的[openJiuwen 样文索引](../samples/openjiuwen/index.md)按题材选择相关段落，默认一至两篇足够，不作为必读数量。样文的正文、图片和来源记录均在技能目录内定位，不依赖项目根目录或代码仓的工作目录。

为本场景新建或重构大纲时，先按[引用性质](../samples/openjiuwen/writing-guide.md#先判断引用性质)区分写法、事实和媒体，再依据[流程中的用法](../samples/openjiuwen/writing-guide.md#流程中的用法)选定相关段落与用途。先围绕本篇证据形成主张，再选样文帮助组织；局部改稿或审稿只读相关条目，不为补齐样文分类扩写文章。

历史数字、发布状态、论文信息及抓取格式的具体处理见[样文约束实例](../samples/openjiuwen/writing-guide.md#从样文提炼的约束)，不把原文已发布等同于本篇已核实。

参考目录不可用时，继续使用本文件中的写作约定与本次材料，并如实说明未读取样文，不假装参考过原文。

## 形成关键差异与竞争力建议

生成大纲相关部分时，以 openJiuwen 的已提供代码、设计方案及相关资料为本方依据，对照竞品特性宣发软文及可用证据，建议值得展开的关键点，不要求存在本方宣发软文。本篇资料按需放在 `refs/design/`、`refs/competitor-articles/` 等英文目录。只处理本篇主题相关的产品与能力，不扩展为全面竞品调研；没有竞品材料时仍可基于本方证据提出能力价值，不强行凑比较对象。

1. **对齐比较对象**：从本方代码及资料提取能力、任务与使用条件，再与竞品宣传的特性对齐，记录产品／组件、版本、资料日期及来源位置；按实际行为比较，不只比较口号。设计方案用于理解设计意图，相关代码用于核实实际接入、链路和限制，不能把规划当成已实现能力。
2. **区分证据层次**：分别说明本方已核实能力、竞品宣发口径和实际演示验证的结果。竞品仅有宣发资料时，对其结论限定为公开宣发口径或侧重点；没有提及某特性、未取得源码或未找到实现，都不能直接推出竞品不支持。比较性能、效果或成本时仍须可比条件与实际数据，单方演示不证明优于竞品。
3. **给出可写建议**：区分双方共同覆盖、证据支持的差异和仍待核实的候选点，优先建议与目标读者相关、能解释技术支撑且可演示的内容。按需用简表呈现“比较维度｜openJiuwen 能力及代码／资料依据｜竞品宣发与依据｜建议表述及证据缺口”，不另建必填报告或状态字段。双方覆盖接近时，可建议从具体任务、使用路径或实现机制细化，不夸大为独有能力。
4. **落到大纲**：每个拟采用关键点给出候选表述、用户价值、已有依据／限制、技术支撑，以及具体 case 和独立编号的视频或图片计划；证据不足的比较判断留在讨论区待核实或收窄，不作为确定主张归档。用户选择与修改并入原有大纲讨论，完整稿最终确认后才归档，不增加独立竞品结论审批。后续新证据改变已确认主张时，沿用大纲变更流程。

## 表达与术语

- 使用简体中文，品牌名写作 `openJiuwen`，产品名写作 `WorkSwarm`；其他名称、大小写与中文译名以本次官方材料为准。
- 开头尽快落到真实任务的阻碍和本次能力，避免大段行业趋势铺垫。已有明确发布消息时，也可先用一段交代更新，再展开价值。
- 用具体动词交代“谁提供什么输入、系统如何推进、用户得到什么结果”。首次出现的重要术语配一句面向读者的解释，不连堆英文缩写。
- 默认采用清楚、积极的技术产品口吻。只有写作身份和材料允许时才使用“我们实测”“我们发布”等第一方表述，不自称亲历实验。
- 为手机阅读组织较短段落和清晰小标题；只在重要能力、关键结论或数字上少量加粗。列表用于并列内容，不让整篇文章变成条目摘要。
- 标题突出具体问题、新能力或可信结果，可有传播感；不机械复刻样文的感叹号、夸张比喻和绝对化措辞。

## 按题材调整重点

以下仅说明推荐骨架如何取舍，不提供另一套固定章序，也不新增公众号场景。

| 题材 | 调整重点 |
| --- | --- |
| 产品或功能发布 | 优先讲清更新带来的任务变化与使用入口，技术深度按受众取舍 |
| 技术机制或架构解读 | 重点展开技术设计与能力的对应关系，按目标版本核对集成状态 |
| 案例或效果验证 | 用任务过程、验收与真实记录组织内容，避免把原因推断当成实验结论 |
| 竞争力或差异化展示 | 默认在接入／使用后集中呈现差异点及演示；比较对象与条件明确，单方案演示不推出其他方案做不到 |
| 生态或社区介绍 | 用角色、资源分工及获取和复用路径解释价值，只保留相关参与入口 |

## 产品表述边界

- 区分 openJiuwen 平台、WorkSwarm 应用与组件、插件各自提供的能力；组件已有实现不代表 WorkSwarm 已完成集成。
- 涉及个人版、团队版和不同操作系统时写清适用范围，保留“已上线、实验中、即将支持、计划支持”的差别。
- 性能数据若依赖算力亲和、特定模型或提前完成的知识整理，应保留这些条件，避免把局部收益写成产品全流程的普遍收益。

## 配图与收尾

按内容需要选择架构图、流程图、界面截图或结果对比图。每张图应帮助读者理解相邻内容，图注包含编号和标题并说明能看到的事实与意义；已规划媒体缺少素材时保留占位及制作要求，不宣称“下图／视频证明”。历史媒体复用按[引用性质](../samples/openjiuwen/writing-guide.md#先判断引用性质)核查，在本篇使用规范命名的 PNG；文件、源图配套及清理遵循媒体规范，来源保留按[追溯规则](../versioning.md#参考材料与历史追溯)处理。

收尾给出适合目标读者的下一步，例如下载体验、查阅接入文档、访问源码或参与共建，并使用本次核实的入口。不默认加入点赞转发、二维码和所有仓库链接，也不把未来展望写成已实现功能。
