# 局部改稿与格式审阅

接续改稿先核对当前正文、绑定大纲和用户指明的范围。用 `preferences` 读取场景默认与本篇约定。明确限定章节、标题或配图时，只改该范围以及必要的同步引用。

## 按用户选择推进

- 要候选或先看方案时，用聊天展示当前候选，或用 `revise` 预览，不传 `--apply`。用户要求逐段确认时，一次只展示一段，分别记录 `accepted`、`keep`、`pending`，采纳项保存该段真实回复。确认完再应用；用户要求先落盘一部分时，只提交已经明确采纳的部分。
- 用户指定精确替换、给出已选文案或明确要求直接改时，用 `direct`，以实际用户指令作为依据。需要自主重写且尚未选定文案时，按章节流程确认；用户已经选择结构和素材、并明确要求把所见修订稿写入当前稿时，直接应用。
- 「用这段替换」承接用户刚选中的文案。后续反馈如「不用加粗」或「同步改视频说明」只应用到指明的段落和媒体。沿用该段已明确的限制，例如省略具体插件名，避免写入时带回已删信息。
- 修改前章时可以在活动工作稿外预览修订。原稿、后续章节和待确认内容都保留。已经确认的无关单元无需重新确认。
- 用户在编辑器里直接改了已确认章节时，用 `reconcile` 查看受影响章节。旧确认稿仍有快照时会显示差异；只有旧散列时，会给出现稿供用户核对。用户采纳后，用 `reconcile --section <ID> --expect-sha256 <现稿散列> --basis <用户回复> --apply` 更新该节确认记录。正文和其他章节的确认记录沿用原文件。
- 发现其他章节有确认差异时，先区分本次目标与待核对章节。可独立验证的目标修改按已有授权落实并保留原有差异，归档前用 `reconcile` 处理确认差异。

## 一次同步正文、大纲和媒体

用 `article_workflow.py revise <软文目录> --plan <JSON 文件>` 预览差异与文件清单，加 `--apply` 提交。计划中的片段使用 LF，每处原文须能在目标范围内唯一定位。以下是逐段审阅的示例。

```json
{
  "mode": "review",
  "basis": "逐段让我确认，确认后同步正文和大纲",
  "body": [
    {"section": "lead", "before": "原导语。", "after": "候选导语。", "decision": "keep"},
    {"section": "main-04", "before": "原段落。", "after": "确认后的段落。", "decision": "accepted", "reply": "可以"}
  ],
  "outline": [
    {"before": "原大纲概述。", "after": "新大纲概述。", "decision": "accepted", "reply": "正文和大纲一起改"}
  ]
}
```

- `body` 按稳定章节 ID 更新；`outline` 同步同版大纲和现有工作大纲。`title` 用同样的 `before`、`after` 格式，自动同步三处文章主标题。已供正式正文使用的大纲沿用版本规则，不能通过此命令改写历史。
- `media` 按稳定 ID 更新已登记的正文媒体。`{"id":"IMG-03","number":1}` 会同步编号、正文图注、引用、匹配的大纲占位、PNG 和同名 SVG，并沿用已有文件名的修订号格式。`title`、`description` 用于更新图注，`format: true` 应用本篇版式。`{"id":"IMG-03","remove":true,"delete_files":true}` 同时撤下图注、链接和对应文件。省略 `delete_files` 时只撤下引用。仍被其他稿件引用的文件会被校验拦下。新素材的取证与采用沿用媒体流程。
- 大纲占位可在行末加 `<!-- media-id: IMG-03 -->`。两份大纲都按此 ID 匹配。未标注的旧占位在读者编号唯一时沿用该编号匹配并补上 ID。预览中的 `outline_media` 会逐份列出匹配、标题不同和未匹配项。
- 正文标题和大纲概述有实质变化时在计划中同时给出对应的大纲改法。自动更新的媒体引用以登记的标准图注块和大纲占位为边界，遇到非标准写法先按实际引用核对。
- 事务校验正文、绑定大纲、工作大纲和素材后批量提交，在 `.drafts/` 保留改前记录。中断用 `recover` 预览并核对，`recover --apply` 继续提交已校验的同一批改动；遇到外部修改时保留现场。

## 本篇偏好与格式审阅

当用户确立需要后续沿用的术语或版式时，可保存为 `article/preferences.json`。一次性修改只在实际稿件中落实。可用字段包括：

- `media` 覆盖场景默认。`image_caption` 取 `below` 或 `above`，`video_caption` 取 `linked` 或 `separate`，`description_required` 为布尔值，`numbering` 取 `appearance` 或 `stable`。
- `global_notes` 为全文约定列表；`sections` 用稳定章节 ID 记录各节要求；`terms` 用 `avoid`、`prefer` 和可选 `sections` 记录用词提醒。只在读者可见文字中检查，代码、命令和链接目标按原始来源保留。
- `long_paragraph` 是手机端阅读的提示阈值，默认 180 字。是否分段、加子标题或改标题取决于本篇写法和用户确认。

用 `article_workflow.py review-format <软文目录>` 审阅当前工作稿，加 `--version <vNNN>` 查看指定版本。工具解析 Markdown，带行号指出显示为普通字符的加粗标记、标题层级、媒体格式与编号、命令和可见占位。长段落和长标题只给提示。结合手机端呈现及本篇偏好筛选问题；审阅本身不写文件。`check` 仍用于版本、确认和素材一致性校验。

案例的功能描述发生变化时，用 `review-media '<软文目录>' --media-number '视频6'` 对照正文前后段落、实际媒体说明和大纲里的对应原文。加 `--version` 可查看归档稿。根据用户提供的功能说明或实物核对三处内容，并按本轮授权处理差异。

需要目视检查时，运行 `article_workflow.py preview-mobile <软文目录> --version <vNNN> --output <预览.html> --apply`。在浏览器打开本地 HTML，查看手机宽度下的标题换行、技术图字号和视频链接长度。预览沿用正文所在目录的图片和链接，适合检查 Markdown 的阅读效果。
